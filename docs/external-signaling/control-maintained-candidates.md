# Opt-in maintained candidate publication

The controlled native adapter can publish bounded same-gameplay-mux STUN observations through the existing authenticated heartbeat. This supplies mapping evidence, not proof of inbound reachability. It does not enable server-assisted joins, diagnostic admission or regional probes.

Two matching explicit choices are required: a transport opened with maintained publication, and `ProviderControlConfiguration` with `NativeOwnership.ISSUED` and `CandidatePublication.MAINTAINED`. Existing three- and four-argument configuration constructors keep publication disabled. Persisted maintained mode cannot silently reopen with it disabled.

The typed native opening API is `NativeProviderTransport.openControlledMaintained(bootstrap, selection, numericStunServers, certificate, privateKey, limits)`. `EndpointSelection` carries the complete configured set or public local hints using the fixed gameplay port. The generic native factory accepts these additional options:

```text
controlMode=nethernet-control-v1
endpointPolicy=explicit-or-public-local
candidatePublication=maintained-v1
advertisedEndpoints=[]
stunServers=[{"address":"198.51.100.1","port":3478},{"address":"2001:db8::1","port":3478}]
```

The STUN addresses above are documentation placeholders; the embedding platform must supply its selected service's actual numeric endpoints. Network performs no STUN DNS/provider selection. The factory binds the disabled gameplay listener before creating its observation controller. An empty direct selection is valid for this opening API. Every configured endpoint remains exclusive across both families, preserves its forwarded port and suppresses controller creation and parsing of unused STUN options. Without configured endpoints, public direct candidates retain precedence independently per family even when reachability is unknown. A missing direct family can use its supplied numeric server. Existing factory callers retain their prior policy and failure behavior.

`MaintainedCandidatePublisher` samples one controller/tracker on the serialized application executor, including while control I/O awaits. Native monitors refresh independently with no players. Failed STUN transactions retain still-fresh successful observations; monitor loss, remap, ineligible mapping, clock failure or lease expiry withdraw reflexive material while preserving direct candidates and the native listener. New successes on the same mapping update lease bytes without changing candidate material. Local interface selection is captured at opening; this slice does not install platform property discovery or DNS refresh.

The first issued-owner claim uses an empty or host-only profile. Reflexive publication begins in a subsequent pass after the original claim's durable acknowledgement attaches to its original physical listener. A publication pass retains its original observation capture, exact native owner and candidate profile through profile reads, immutable journal writes, signing, actual carrier send, result delivery, application persistence and final applied/ready exchange. These guards perform no native reads or I/O. New same-mapping successes preserve older still-live captures; material changes, closure and original deadlines revoke them. An unresolved lease-bearing heartbeat, including `acceptingPlayers:false`, requires authenticated status/cancellation when its original live capture is unavailable. Restart never reconstructs authority from historical receipt metadata.

Every `candidateLeases` request requires a strict `candidateLeaseReceipt` response matching all of `hostProfileRevision`, `profileSha256`, `acceptedSha256` and the minimum original expiry (zero for an empty document). The receipt is saved with its exact associated profile and is historical metadata, not a player application basis. Unchanged/full-profile-key rebindings retain original observation dates. Pure revision-only renewal keeps the profile, ticket policy and application basis unchanged, so the existing native installation is reused. Renewal is piggybacked on heartbeat cadence, capped to request another check-in at least 30 seconds before the accepted observation expiry. Final empty publication reports `acceptingPlayers:false` while retaining a truthful native serving basis and established peers. No ordinary WebSocket frame gains a database operation.

Validation includes deterministic publisher/controller/tracker tests for unchanged success, failed refresh, independent families, expiry, clock recovery and remap/ABA; application tests for exact receipts, renewal without reinstall, key rebind, immutable retries, restart rejection and remap during send/await/save; and native tests using both families of the same gameplay mux. The native maintained test receives three real Binding responses per family with deliberately synthetic public mapping attributes, and keeps two signed DTLS/SCTP peers exchanging data through renewal, remap, withdrawal and restoration. It uses a signed 55-second test ticket because the transport-only fixture deliberately never completes the later game identity proof; production ticket limits are unchanged. This is not a regional reachability or stock-gameplay result.

The matching provider must atomically accept owner/profile/observation association and retain replay high-water, propagate original lease bounds through cached routing, and guard final answer delivery. Those provider consumers and the separate Java/Worker/D1/KV maintained-publication replay are independent integration gates. No default configuration, Geyser integration, production deployment or remote publication is enabled by this change.
