# Controlled application readiness

`ControlClientIo.synchronize` returns a typed `ControlSynchronizationResult`. Null or an ordinary completed task cannot establish READY. The application adapter must actually apply and durably save its state, then call its current `Synchronization.applied(AppliedBasis)` once. The coordinator owns the confirmation and compares the generation and complete basis digest against its provider-signed cached authority summary. A mismatch returns `awaitingSource` and uses bounded cached-authority backoff; it does not poll strong status or replace a healthy socket merely for propagation lag.

HTTPS confirmation uses the exact current signed source summary. WebSocket confirmation additionally sends one machine-signed `state.applied` with a fresh synchronization ID and the coordinator's physical frame sequence, then requires a matching provider-signed `session.ready`. Local send completion and the matching response are both required. Earlier synchronization IDs cannot confirm a new pass. Confirmation is bound to the originating exchange, source, writer, key catalog and fixed deadline; it cannot be reused by another pass. A desired-state notice after application cancels the pass.

Application code still owns native-instance tokens, serialized application work and durable storage. It must check its application/transition ownership as well as `exchange.requireCurrent()` before and after each asynchronous effect. This coordinator cannot prove that a caller actually applied native state. It does not install keys, bind a listener, set native admission readiness or create a ProviderClient adapter.

Only one readiness send may occupy a physical connection. A timed-out response does not release an unfinished underlying send; later source refreshes cannot enqueue another until the send settles. Failed or throwing handoff has ambiguous peer sequence consumption and requires physical recovery. A failure before handoff consumes no frame sequence. Cancellation completes waiting confirmations only behind transition fences, so completion callbacks may close or replace the coordinator without an outer transition resurrecting it.

One in-flight application frame may arrive ahead of readiness during resynchronization. The coordinator authenticates and consumes its sequence but retains the frame without application dispatch, allowing the ordered readiness response to pass. It dispatches only after READY under the original source, signing key, attempt, synchronization and frame deadline. The combined unauthenticated-source quarantine and consumed application buffer retain at most one frame. A second application frame or loss of the retained frame's scope requires physical recovery once positive authority is available. The abandoned socket is fenced before replacement; old frame replays cannot disrupt the replacement. An application enqueue failure also recovers the stream and cannot leave READY set.

Local validation on 15 September 2026 passed all 166 control/coordinator/file-journal tests in 17 seconds, including exact-source mismatch, null completion, stale synchronization IDs, send/response ordering, stalled send occupancy, signing-time expiry without a sequence gap, cancellation callback reentrancy, queued application ordering, buffer overflow, source replacement and enqueue failure. Independent review identified and drove regression coverage for the cancellation, send occupancy, sequence and deferred-dispatch races.

Reproduce with `./gradlew :external-signaling:test --tests '*Control*' --tests '*FileControlClientJournalTest' --init-script /tmp/warden-diagnostic-host-native.init.gradle --console=plain -x :external-signaling:nativeAdmissionTest` in the local unpublished native dependency environment. These tests use signed fixtures and a controllable I/O adapter; actual ProviderClient, Worker socket-owner readiness, native application persistence and cross-isolate E2E remain separate gates.
