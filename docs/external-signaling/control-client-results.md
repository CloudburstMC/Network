# Operation result and initial heartbeat integration

The optional coordinator consumes the shared [operation-result envelope](control-v1.results.md) over HTTPS and signed `lifecycle.receipt` frames. Both carriers allow at most 65,536 envelope bytes and 45,056 decoded body bytes. A normal result always has a body; noncommitted receipts require exactly the original UTF-8 bytes `{}`. Application response objects may contain negative, fractional and exponent numbers. Parsing is strict about UTF-8, canonical base64url, duplicate object names, object roots and nesting, and preserves the exact original bytes.

`submit` and `rotateMachineKey` return `CompletionStage<ControlOperationResult>`. The coordinator verifies the existing receipt against the retained original intent before using either receipt or body. A committed ordinary result clears the durable intent before notifying application callbacks. Opted-in outcomes first persist the receipt and finish the application queue acknowledgement before clearing their barrier. The local DTO owns its bytes, redacts its body from `toString`, and never writes response bodies or one-time secrets into the generic journal. HTTP result bodies depend on exact trusted TLS method/target provenance. WS bodies additionally depend on the exact captured provider frame-signing key tuple and current source authority, even when the frame and authority use different trusted provider keys.

`bodyBytes()` is optional because a signed status query can recover a committed receipt without recovering its original body. Such reconciliation returns an absent body, not an invented empty successful heartbeat. Rotation likewise reconciles the persisted candidate credential and receipt before releasing commit knowledge; it does not replay the first response body under the old key. The controlled ProviderClient applies fresh responses on its serialized application executor; receipt-only recovery performs a new state exchange. Unknown receipts retain the original intent barrier. Verified rejected, expired or native-replacement cancelled receipts release the original barrier without a body or readiness claim. Cancellation is a separate signed current-writer action, never inferred from a transport timeout.

Every delivered body carries a live local guard. The original request/frame deadline, fixed session expiry, physical writer, selected machine key/revision, captured WS signer and applicable source/synchronization authority must remain valid. A newer authority proof never extends an old result's delivery lifetime. Recheck `result.requireCurrent()` immediately before and after asynchronous application. A journal write may reenter the coordinator or outlast authority; its final guard can preserve committed receipt knowledge while withholding the now-stale body. Once copied, bytes cannot be recalled by the coordinator: the typed adapter is responsible for avoiding stale application and for its own secret persistence rules.

## Restricted initialization lane

`ControlClientIo.synchronize(writer, grant, verifiedAuthority, exchange)` receives a short-lived `Synchronization` handle. Its owner must apply real state and keys and observe provider readiness for that exact binding before completing its returned stage. Receiving a receipt, response body, cached proof or open socket alone is insufficient. The coordinator also performs a final authority/key/floor/writer check and refuses readiness while a heartbeat owned by this handle remains unresolved.

During synchronization, normal `submit` and `rotateMachineKey` calls are rejected. `exchange.heartbeat(originalBody)` is the only initial operation lane. It uses the selected writer transport: a WebSocket writer sends a signed lifecycle frame, including during initial synchronization once cached authority is installed. An HTTPS writer or body larger than 45,056 bytes uses the exact configured HTTPS endpoint. A WebSocket error never silently chooses HTTPS. This carrier choice does not perform a transport CAS. It uses the same persistent original intent, monotonically increasing operation sequence, one outstanding operation and receipt barrier as normal operation delivery. `pendingHeartbeat()` returns owned exact bytes when an earlier heartbeat still needs recovery; a supplied retry must match those bytes. A retained non-heartbeat intent cannot be silently replaced. Unknown heartbeat bytes may retry only while their application claims remain valid. Recovery of a retained native acknowledgement checks signed status first and, if unresolved, uses explicit terminal cancellation under a selected current writer before reapplying on the replacement native instance. No second sequence owner is introduced.

Adopting a heartbeat whose earlier WebSocket send is still awaiting a receipt does not start a concurrent HTTPS delivery. If that earlier acknowledgement was lost, adoption alone does not recover it: the existing explicit receipt reconciliation or transport-recovery path must settle the retained intent. The adapter must not treat an unresolved operation future as successful state synchronization. A lost WebSocket receipt reaches the bounded status reconciliation path at its original frame deadline; a healthy socket may be retained, while a lost physical socket requires a new activation.

The handle is bound to its attempt, synchronization generation, installed verified source proof, writer, fixed grant and fixed synchronization deadline. Both HTTP proofs and WebSocket frames are capped by that original absolute deadline, even when application work was queued or earlier heartbeat rounds consumed most of it. Supersession, key retirement, timeout or closure invalidates it. A late response may still supply independently valid commit knowledge, but its body is withheld from an invalidated synchronization owner. Normal operation receipts during an already-running synchronization cannot bypass the same barrier.

The concrete adapter must use its serialized application executor for parsing/applying bodies and state/key updates. Callback completion can reenter the coordinator monitor; do not block that monitor waiting for application work. The application chain should perform these steps:

1. Recheck `exchange.requireCurrent()` and choose the retained heartbeat bytes, if present, or construct the real initial heartbeat.
2. Request `exchange.heartbeat(bytes)` and offload its continuation to the application executor.
3. Require both the exchange and result to remain current, parse the owned original body and apply the actual desired-state/key response.
4. After asynchronous application, recheck both guards and wait for the actual matching provider readiness confirmation.
5. Complete the synchronization stage only after both application and confirmation finish; propagate missing bodies, application failures and stale guards as failures.

State application must complete inside the original bounds. A short response deadline is not extended to make slow application succeed. A receipt-only recovered heartbeat requires a new explicit state exchange, not synthetic success. There is no idle heartbeat, authority or D1 polling loop in this integration seam.

## Validation and remaining integration

The codec fixtures cover exact original bytes, different mutable retry observations with the same immutable receipt, rotation output and noncommitted bodies. Shared schema and independent signatures are checked in both languages. Coordinator tests cover both carriers through controlled I/O, byte ownership, body redaction and absence from journal snapshots, wrong-intent/legacy-receipt rejection, receipt-only recovery, writer/deadline/key fencing, reentrant key retirement after a durable commit, retained-intent adoption and noncommitted barriers. An application executor test requires actual test-state application and a correctly signed provider readiness frame before the coordinator becomes ready.

These unit tests use explicit provider fixtures. The reachable controlled ProviderClient now implements response extraction, durable native application and typed readiness; separate tests cover the real JNI listener and Java/workerd integration. The live-carrier release gate additionally requires the actual runtime to complete initial and periodic WebSocket lifecycle exchanges more than 30 seconds after upgrade, reconcile a lost reply and replace a lost socket without hidden HTTP fallback. No fixture or native readiness result establishes stock-client gameplay or regional deployment.
