# Client source authority renewal

The optional coordinator obtains authority through the separately signed authority codec. `Config.authority` is an explicitly trusted HTTPS POST endpoint, conventionally `/control/authority`. `ControlClientIo.authority` returns a raw `HttpReply`; the coordinator checks the exact requested method and URI, response URI, 8 KiB limit, original request digest, selected writer/key/capabilities and provider-control signature. This does not advertise a new ProviderClient capability or mount any provider route.

The request has a fresh nonce and immutable delivery/requested-authority deadlines. A response can replace expired source authority because it is verified independently against the fixed session and trusted provider-control catalog. Source expiry remains at most 300 seconds after the authoritative source check; receiving a proof does not slide it. Unavailable, invalid or timed-out refreshes retain the physical connection and writer epoch. Their bounded jittered retry uses only the authority endpoint, with no call to the strong bootstrap/status/CAS path. One underlying authority request and one state-application operation may remain outstanding; timeout does not free their slots until they settle. Integrations must still bound their actual I/O deadlines. Initial synchronization, an explicit `synchronize()` call, or pending protected work creates refresh demand. Idle expiry changes state without starting a polling loop.

Before installing a proof, the client rechecks the pending nonce, attempt, exact current writer and credential, trusted signing-key tuple, latest source floor and short delivery deadline. The source floor is durably written first. Disk writes and completion callbacks may reenter the client, so installation repeats those checks after persistence. A failed journal write halts the client before further delivery. The journal stores the original signed authority response solely as a rollback record: loading it never restores live authority or readiness. Snapshot changes and selected-key rotation retain it; both coordinator and file journal reject removing or regressing it.

`ControlClientIo.synchronize` receives the verified proof and a restricted coordinator-owned heartbeat lane, then returns `CompletionStage<Void>` only after required state and keys have been applied for that binding and the provider confirms readiness. The lane shares the same durable intent and sequence barrier; it must not be implemented by a second lifecycle owner. See [operation result integration](control-client-results.md). It cannot mint authority. Completion checks the current installed proof, inner expiry, writer, source floor and signing catalog. It does not reuse the already-consumed delivery deadline. Initial activation and a positive refresh response alone do not establish `READY`. Ordinary frames and lifecycle operations keep their existing individual deadlines and sequence rules; the fixed session is never substituted for expired frame authority.

While authority is unavailable, the client retains at most one authenticated bounded ordinary frame without consuming its sequence or dispatching its payload. A second distinct authenticated frame records a gap and retains one frame as evidence; exact duplicates and unverified garbage do not displace it. A fresh source proof is required before processing the retained frame or replacing the writer because of a gap. State synchronization frames can then drive synchronization; application frames wait for readiness. The same bound applies during state application, so a later synchronization frame cannot silently disappear behind retained application work. A retained expired, conflicting or out-of-order frame justifies an explicit replacement only after rechecking its provider signature and current physical/session binding under current provider-key trust. That signature is evidence of a lost ordered frame, never permission to dispatch an expired payload. Once a gap requires replacement, callbacks from that discarded physical connection are fenced, preventing repeated arrivals from creating repeated CAS attempts during the transition. Retry backoff resets only after both authority verification and state application succeed; repeated state failures do not turn successful proof fetches into a rapid retry loop.

Tests cover source lag beyond the old authority expiry without strong polling, exact HTTPS provenance, late responses and stale nonces, durable-floor rollback/reopen, selected writer/key changes, journal reentrancy and delivery overrun, synchronization across the delivery deadline, and authenticated versus forged frame quarantine. Native transport regression tests remain separate evidence; this coordinator does not change gameplay listeners, established peers or NAT traversal.
