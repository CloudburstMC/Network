# Controlled diagnostic completion delivery

The existing `Diagnostics.ENABLED` controlled-client opt-in now drains native diagnostic results independently of player outcomes. Legacy clients and diagnostics-disabled controlled clients do not poll or upload them. Reports use `DiagnosticCompletionEmitter` and preserve the original admission binding, key, target, timestamps, selected path and counters. A new native owner may deliver historical reports; reports alone do not claim current native readiness.

The root `provider-state.json` owns `controlDiagnosticCompletions` under the existing private state-store lock and atomic write. Its separate `pending` array contains at most32 immutable reports. Once per second the application lane polls no more than4 results, and does not poll again while that drained RAM batch awaits a successful root write. The queue is merged with the current application, credentials and player-outcome root; it never saves a stale root copy. Player-outcome capacity reserves space for diagnostic records and their metadata. Heartbeats select at most4 reports from the original queue head, reducing the prefix if necessary to fit the WebSocket lifecycle body bound. Insufficient heartbeat capacity leaves the queue intact.

A retained lifecycle journal owns the exact original heartbeat bytes. The coordinator persists its authenticated COMMITTED receipt before invoking diagnostic settlement, composes native-owner adoption and diagnostic acknowledgement when both occur in one heartbeat, and holds actual callback occupancy until local settlement finishes. Queue removal and a compact acknowledgement marker are one durable root write before the pending lifecycle entry is cleared. The marker contains the intent, receipt and original body digests, sequence and `settled` flag. An already-settled marker makes recovery after failed journal clearing idempotent.

Every optional diagnostic receipt must match an original submitted full installation binding, attempt ID and canonical full completion digest. The entire batch must match before any report is removed. A recorded receipt must retain its original receive grace (`completedAt <= receivedAt <= expiresAt + 300000`); every receipt must precede or equal its parent lifecycle commit. Rejected dispositions can acknowledge unmatched/future-time reports and increment `unknown`, never a transport/firewall failure. Recorded receipt settlement increments `recorded`; this is upload accounting, not independently correlated reachability.

Missing or malformed optional receipts preserve the queue and increment a bounded `unsettledBatches` counter once per intent. They do not invalidate an otherwise healthy player response. Strong status and cancellation recovery provide only the parent lifecycle receipt, so an un-settled prefix remains for a fresh authenticated heartbeat carrying the same report bytes. The provider's exact report retry returns the original recorded receipt time. No response secrets are journaled. A safe decoded receipt batch may remain in RAM across a failed root write; process restart instead uses the bodyless recovery path.

`invalidNative` counts unusable or conflicting native observations. `nativeDropped` counts observed native overflow-counter deltas after establishing this process's baseline. A reset does not manufacture recovered counts. `priorProcessLossUnknown:true` and a startup diagnostic notice explicitly retain uncertainty about an earlier process's never-persisted native/RAM results. This implementation cannot recover bytes that a process lost before its first successful durable write. A full durable queue stops polling; native overflow remains separately accounted where the native counter is available. None of these counters assert a firewall failure.

Tests cover disk-write failure, actual state-store reopen, preserved unrelated root writes, queue/poll/body bounds, original-byte and full receipt association, both-family report conversion, old native owners, callback timeout, status/cancellation recovery, owner-plus-completion hook composition and healthy-player no-churn behavior. Coordinator tests use protocol carrier fixtures; they do not establish a deployed Worker roundtrip, regional reachability or gameplay. Separate integration evidence must prove those scopes.
