# Controlled client integration

The optional controlled profile is reachable through `ProviderClient.Configuration.control`. It requires explicitly configured exact routes, a trusted provider-control public catalog, an already enrolled/reconciled registration, and a listener created with `NativeProviderTransport.openControlled`. Provider discovery, new enrollment, and public server route mounting remain separate integration gates. Legacy configuration keeps its existing lifecycle; a durably controlled host cannot fall back to it.

`ControlClientCoordinator` exclusively owns one `ControlClientJournal` and serializes callbacks, lifecycle intents and control-session transitions. Construct it with the expected provider subject, explicitly trusted route URIs, the separately trusted provider-control verification key ring, one shared `ControlClientClock`, a non-blocking scheduler, and `ControlClientIo`. Production identifiers must use at least 128 cryptographically random bits; `secureIdentifiers()` supplies 192. The injected identifier supplier exists for deterministic tests and is trusted configuration.

`FileControlClientJournal` uses a **dedicated** control directory. The controlled `ProviderClient` owns the existing root lock and creates this journal in its `control-session` child directory. Migration commits the exact existing credential and sequence floor there before removing machine credentials/sequence from the application document and writing the durable mode marker. No network runs before both commits; only an exact pristine interrupted import may finish after restart. Missing/conflicting journals, pending legacy rotation, stale reporting/sequence baselines, and configuration downgrade fail closed. Supply the generation, last acknowledged revision and reported state as an explicitly reconciled migration seed: legacy saved state does not provide that revision reliably. The seed grants no native application knowledge. The journal atomically persists the selected key, candidate private key, original body, stable intent and any pending bootstrap before a network send. It reuses exclusive file ownership, atomic replacement, file fsync and POSIX directory fsync from `ProviderStateStore`; it adds strict bounded decoding and owner-only POSIX/ACL permissions. Windows ACL and crash-durability behavior still require a real Windows acceptance run; directory fsync is unavailable there. Unsupported permission filesystems fail closed. A commit failure clears authority, fences callbacks and closes control connections, retaining the journal for recovery.

Readiness progresses through strong reconciliation, prepare, standby, activation and explicit synchronization. An open socket, persisted grant, historical activation receipt, or `writerEnabled: true` status never establishes readiness by itself. Only the current physical binding may deliver active frames. During synchronization the coordinator owns typed `session.ready` confirmation; verified `session.resync` and `state.desired` can notify the application adapter. Other application work waits for ready. The adapter calls the restricted exchange only after actual native application and durable storage; the coordinator compares the exact basis to current signed source authority. HTTPS confirms that same source basis locally; WebSocket additionally requires its signed acknowledgement with the matching synchronization ID and successful send handoff. Missing synchronization or mismatched source fails closed. The original exchange deadline is fixed when the coordinator starts the pass, never when queued application work begins.

Lost lifecycle acknowledgements preserve the same original intent and bytes across retries, restart, writer replacement and machine-key rotation. Unknown receipts retain the single-intent barrier. Verified terminal rejected/expired/native-replacement-cancelled receipts release it while preserving the sequence floor and original selected credential; they expose no application body and cannot prove candidate selection. Rotation persists its host-selected candidate ID and private key before sending. Recovery first tries strong candidate-key status, reconciles the original immutable receipt, then promotes the candidate atomically. If candidate status is unavailable (including generic 503, timeout or transport failure), the same bounded reconciliation cycle makes at most one independent old-key status attempt. Failure never identifies the selected key or proves rejection: only a positively verified status can continue, and failure of both queries retains the original intent/candidate and enters the existing backoff. Late candidate callbacks cannot displace the old-key attempt. A live successful rekey resynchronizes the same epoch/socket and preserves its frame sequences. Status alone cannot select a key supplied by an untrusted frame.

A committed deregistration receipt is terminal for this control generation. The coordinator durably retains its exact intent and committed receipt in the existing pending-record shape as a terminal marker, enters `DEREGISTERED`, fences callbacks, and closes only its control connections before completing a receipt-only result. It does not expose or apply an application body. A restarted coordinator recognizes the marker before any status, prepare, activation, authority-refresh or heartbeat request; historical grants cannot reactivate it. Unknown, rejected or expired receipts do not establish terminal success. A journal failure preserves unresolved work and cannot report successful local termination. Actual gameplay drain/shutdown remains the application adapter's responsibility.

Prepare retries retain the exact original payload and fixed intent deadline. Activation is journaled before send. An ambiguous activation can only be discarded after a new strong status request was issued beyond the original proof deadline plus the explicit 30-second clock uncertainty bound and still reports the expected writer. A reply delayed across expiry cannot establish that fact. A committed activation recovered after process restart preserves its original fixed grant and then replaces the lost physical socket through another CAS.

An operation over HTTPS retains the current WebSocket writer identity; bodies over 45,056 bytes automatically use that carrier and preserve the 65,536-byte core body ceiling. Persistent HTTPS fallback explicitly prepares and activates a new epoch with request-response capability only. Planned socket rotation is scheduled before the fixed session expiry with a 60–300 second jittered lead, capped to a quarter of short session grants. Unexpected loss uses exponential equal-jitter backoff, including the first reconnect. Source authority expiry stops transient readiness without creating an idle per-host status polling loop. Established gameplay and native admission are outside this coordinator's ownership and are never closed or recreated here.

`ControlClientIo` is an integration boundary, not an alternate verifier. Its HTTPS implementation must use normal TLS validation to the exact trusted discovered origin and route, disable redirects, bound response bytes, and provide accurate request/response provenance. Only a bounded operation-result envelope from that authenticated HTTPS exchange, or a verified active provider frame, can acknowledge an operation. The immutable receipt and original response-body bytes remain separate: only commit knowledge releases the intent barrier, and response observations or one-time secrets never enter the generic journal. The application must recheck the returned body guard before and after applying it on a serialized application executor. Receipt-only status recovery exposes an absent body. See [operation result integration](control-client-results.md) for the restricted synchronization heartbeat lane and remaining typed provider integration obligations.

`JdkControlLink` adapts the existing bounded JDK WebSocket transport, enforces canonical WS/WSS origin/target association and hard receive/send caps, and negotiates `nethernet-control-v1`. `JdkControlLink` places the signed upgrade proof in the exact `Nxs-Control-Proof` header. `JdkControlHttpTransport` supplies bounded prepare/activate/status/authority/lifecycle requests with normal TLS and no redirects. `JdkProviderControlIo` connects both to the actual controlled runtime using the explicit route/catalog configuration; it performs no discovery and imports no response-provided trust.

Validation includes signed provider-response execution tests for lost acknowledgements, restart, standby/readiness, delayed strong status across expiry, live rekey, planned replacement, one-off HTTPS, physical callback fencing, durable write failure and monotonic clock aging. Real WS/WSS fragmentation, receive demand, bounded serialized sends, TLS rejection and close cleanup remain covered by `JdkWebSocketTransportTest`. These tests do not establish production routing, NAT traversal or stock-client gameplay.


## Actual application and scheduling

`ControlledProviderApplication` runs on the serialized application executor and chains native futures asynchronously. It never waits on that executor with `get`, `join`, or sleeps. It stages before installing key snapshots, writes durable application state, then commits only the same live transition token under current delivery/authority guards and the original absolute monotonic deadline. Failure or late callbacks cannot enable admission. Stored basis/profile/policy records are recovery input only; a new native instance installs and validates again before acknowledgement.

The first key request delivers one-time material. The client installs/saves it, publishes its actual profile with the active key last in the installed IDs, applies the returned profile revision and complete expected epoch policy, then acknowledges that basis on a subsequent heartbeat **without republishing unchanged profile content**. Native installation order is separate from canonical policy sorting. Fixed retired cutoffs cannot extend; missing required material fails closed. Source-only retries reuse the still-current live basis without extra heartbeat/profile writes. Health and check-in demand use the same restricted synchronization lane and selected carrier. WebSocket writers send signed initial and periodic lifecycle frames; HTTPS writers and oversized request bodies use HTTPS. Neither WebSocket handoff failure nor reply loss silently changes carrier. Missing check-in metadata grants no lease. Outcome delivery remains bounded, persisted and at least once; immutable lifecycle receipt recovery does not replay secret bodies.

Desired nonserving state requires actual native application. Temporary bootstrap staging is reported through `acceptingPlayers:false`, not as a synthetic closed/draining host state. Explicit permanent drain cannot be reversed locally. Warden currently also makes an acknowledged nonserving provider lifecycle draining; same-generation resume requires a separate explicit provider transition and is not silently recovered here. Generic extension operations and assisted dispatch are not enabled by this first configured integration. Controlled machine rotation and deregistration use the coordinator journal; normal shutdown closes the native listener and control runtime without inventing a deregistration receipt.

## Local smoke

`writeControlledProviderLocalSmokeLaunch` emits an argv file for `ControlledProviderLocalSmokeClient`, a separate test-only main. Its owner-only JSON supplies exact loopback HTTPS routes, an ephemeral public provider catalog/test CA, reconciled per-host registration data, and loopback native DTLS identity/ports. It runs actual `ProviderClient` and `openControlled`, emits metadata-only journal/application observations, and reports ready only after the real client completes and the live native profile/serving state match. The parent workerd harness owns source publication; no production IO test callback or cache shortcut is installed. The child has a fixed 180-second run bound and waits for explicit `stop`; `stopped` follows actual native termination. Neither native readiness nor this fixture establishes stock-client gameplay.

The optional JSON boolean `runtimeCheck: true` waits at least 35 seconds from the instant all configured hosts have first reported `ready`, then calls each actual `ProviderClient.readiness()` exactly once. Journal/application observation continues while those returned futures are pending. Each successful future is followed by the same current native serving/profile and saved basis checks as startup before emitting `runtime_ready`, with `hostId`, `transport`, `nativeServing: true`, `nativeProfileMatches: true`, the current `basisSha256`, and `gameplay: false`. Its `elapsedSinceInitialReadyMillis` uses the same shared monotonic all-ready timestamp and is at least 35000. Omitted or false preserves the existing startup-only behavior; the fixed child deadline and explicit stop protocol are unchanged. The parent harness still owns runtime phase orchestration and public source publication.

Controlled application validates the live listener before constructing every fresh native acknowledgement. A failed save fences admission and stops the runtime, including a key-request save made after readiness. Failed transitions and profile changes await admission disable before releasing their synchronization lane. An unresolved retained heartbeat claiming native application is never replayed on a replacement listener. Recovery checks signed receipt status first, then selects a current physical writer and uses the explicitly configured `cancelIntent` route before authority/state synchronization. A committed original receipt wins; a signed cancellation releases only that original sequence barrier. Without the optional route, recovery retains the intent in explicit reconciliation-required state.

Controlled outcomes use the coordinator's opt-in durable acknowledgement hook. A verified committed receipt is saved with the original pending intent before root application storage removes the exact event prefix and records an idempotent intent/receipt/batch marker in the same write. Only then may the coordinator clear its pending barrier. Either crash window replays local acknowledgement; it cannot create a second network intent for the same retained batch. Hook timeout does not release unsettled work, and no response body or one-time secret is journalled. Native polling is bounded by retained count/byte capacity; a drained batch stays in memory until its root write succeeds. The bounded native queue's existing drop counter still describes native overflow.

Cancellation uses the existing bounded session POST transport with exact route provenance and provider-control verification. It requires neither old cached authority nor readiness; the provider still checks the current selected writer/key. The body policy runs only for retained/recovering intents, so the first original heartbeat is sent normally. Delayed/invalid/unavailable cancellation responses never release the barrier, and retries use bounded reconciliation backoff. Incoming socket frames cannot start cancellation before the strong status/activation phase finishes. The local smoke accepts optional `routes.cancelIntent` without guessing a path.

Both carriers cap synchronization heartbeat proof/frame expiry by the original application-pass deadline, preserving the immutable session/source bounds. Outcomes select the writer carrier and retain their durable local acknowledgement hook. See [lifecycle scale acceptance](control-lifecycle-scale-acceptance.md) for the separate measured D1 cost/throughput release gate.
