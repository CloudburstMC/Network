# Draft diagnostic host completion receipts v1

These public receipts settle upload of original native host observations. They are not reachability verdicts, signatures or permissions. The signed **committed** lifecycle response independently establishes durability. The neutral Java codec and optional original-byte heartbeat extraction define the wire boundary; durable queues, application acknowledgement and authenticated storage are separate integrations. Consumer delivery records identify which integrations have been implemented and validated.

An individual receipt is a closed JSON object, with canonical fields in this order:

```text
{installation:<original ControlDiagnosticBinding>,attemptIdHex,completionDigest,receivedAt,disposition}
```

`installation` is the full original admitting binding. `attemptIdHex` is lowercase 16-byte hex. `completionDigest` is the canonical base64url32 SHA256 identity from the complete public host report's existing completion domain; it is the digest of the **submitted** report, including for conflicts, never substituted with another stored report. `receivedAt` is a positive safe integer in Unix milliseconds. `disposition` is exactly `recorded`, `unmatched`, `expired` or `conflict`. There is no individual version or receipt-specific cryptographic domain. Fixtures' `wireSha256Hex` values only record independently generated wire-byte provenance.

The batch is `{version:1,receipts:[...]}`. Individual encoded receipts are bounded to 2048 UTF-8 bytes; a batch is 1..4 receipts and at most 8704 UTF-8 bytes. Repeated `(providerOrigin,hostId,authorityIncarnation,generation,nativeOwnerEpoch,nativeIncarnation,attemptIdHex)` identities are rejected, even across different profiles, policies, digests or dispositions. Historical results from a distinct native owner remain distinct. Original JSON duplicates, alternate/lossy integer spellings, noncanonical binding/base64url and additional or missing fields are rejected. Decoder syntax alone cannot check whether an `expired` receipt is correct: that requires the original completion and authenticated arrival time.

The optional top-level heartbeat field is `diagnosticCompletions`. Request value is the existing `{version:1,completions:[1..4]}` batch; response value is the receipt batch. It is separate from `diagnosticAdmission` installation/ACK. Absence is optional; explicit `null`, empty batches and the wrong direction are invalid. The full original heartbeat is limited to 65536 UTF-8 bytes. The existing original-byte extractor validates the entire body's syntax and duplicate fields, preserves unrelated ordinary telemetry decimals, then passes the unmodified nested slice to the strict typed codec. An escaped spelling of the root field is recognized; duplicate aliases or duplicate unrelated fields cannot be hidden by `JSON.parse`/Gson.

`receivedAt` means the immutable DB reservation time **after authenticating the exact original lifecycle intent and body digest**, not the eventual commit or render time. For a recorded report it is the original first accepted receipt's arrival time. For a rejected observation it is this exact lifecycle transaction's original arrival time. Grace eligibility checks completedAt<=receivedAt<=attempt.expiresAt+300000; successful completion itself remains strictly before its original execution deadline. A late retry may durably settle an unchanged, timely-arriving historical body under fresh current control authentication. It cannot replace the original body/binding, reset receipt time, resurrect a cancelled/rejected lifecycle intent, extend observation freshness or bypass normal current commit authorization/deadlines.

Storage must associate `recorded` with the original immutable claim ACK/acceptance marker and issued offer body/SDP/key/target/host identity. The prober result need not exist yet. Current authenticated host credentials authorize upload, while the report's historical native owner/profile remains original; requiring today's native owner would lose valid recovery history. Exact report retry returns the original stored receipt. Conflicting reports never overwrite the original. Unmatched/expired/conflicting submissions settle local upload accounting as unknown; they do not create fabricated attempt records or become target-firewall failures. Rejected receipt bytes remain fixed in their existing heartbeat journal even though no new host observation row is created. Dispositions must reflect actual atomic storage outcomes under the parent heartbeat authorization fence, without optional diagnostic expiry independently blocking a healthy player heartbeat.

Java queue integration must durably retain at most 32 host records, reserve an exact head of at most 4 without removing it, and journal the exact heartbeat body. Only a verified committed lifecycle response with receipts matching every submitted original identity and completion digest may settle that prefix. Persist the queue update and idempotence marker before clearing the coordinator's retained pending receipt, so crash/retry/status recovery cannot lose or double-settle observations. `recorded` records are still host-only evidence until independent correlation. Nonrecorded dispositions remove or explicitly quarantine the submitted item with unknown/loss accounting; they never imply failed transport. Historical `diagnosticCompletions` alone are not a new native-install or accepting-players claim. No queue or application behavior is implemented by this codec milestone.
